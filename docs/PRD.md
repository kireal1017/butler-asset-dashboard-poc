# 버틀러 자산 현황 대시보드 PoC — PRD

작성일 2026-10-05 · 대상 독자: 이 프로젝트를 구현하는 Claude Code

## 0. 이 문서를 읽는 방법

- 이 문서는 새 프로젝트의 유일한 요구사항 문서다. 빈 폴더에서 시작한다.
- 10장의 개발 단계를 순서대로 진행한다. 각 단계의 "완료 기준"을 통과한 뒤 다음 단계로 넘어간다.
- 외부 API의 응답 구조는 추측하지 않는다. 1단계(M0)에서 실제로 호출해 확인하고, 이 문서와 다르면 실제 응답을 따른다. 다른 점은 `docs/api-notes.md`에 적는다.
- 12장의 "가정" 목록에 있는 값은 그대로 구현한다. 가정을 바꿔야 할 이유가 생기면 구현하기 전에 사용자에게 묻는다.
- 인증키는 프로젝트 최상위 `.env`에 이미 들어 있다. 키를 화면, 로그, 커밋, 문서에 출력하지 않는다.

## 1. 배경과 목표

버틀러(Butler)는 임대인을 위한 부동산 자산관리 서비스다. 기획서는 자산 현황 대시보드를 "국토부 실거래가 및 건축물대장 API 연동을 통한 자산 가치 실시간 트래킹 모듈"로 정의한다. 그런데 단지 시세와 실거래가 그래프는 기존 무료 앱이 이미 제공하므로, 그대로 만들면 차별점이 없다.

이 PoC의 제안은 **시세가 아니라 "내가 산 가격 대비 지금 가격"을 보여주는 것**이다. 임대인이 호실(동·호)을 등록하면 층 단위로 거래를 좁힐 수 있고, 취득 연월만 입력받으면 실거래가 자료에서 그 사람의 매입 거래를 찾을 수 있다.

PoC가 증명해야 하는 것은 세 가지다.

1. 임대인이 단지와 동·호만 입력해 실제 호실을 등록할 수 있다.
2. 등록한 호실의 최근 실거래가와 추이를 더미 데이터 없이 실제 공공데이터로 보여줄 수 있다.
3. 취득 연월만으로 매입 거래를 찾아 "매입가 대비"를 카드와 그래프에 표시할 수 있다.

## 2. 범위

### 포함

- 자산 등록: 단지 검색, 동·호 입력, 전용면적·층 자동 조회, 자산 추가와 삭제
- 매입 거래 매칭: 취득 연월 입력, 후보 확인, 실패 시 매입가 직접 입력, 매입가 수정과 삭제
- 홈 화면: 자산별 카드(최근 실거래가, 거래 시점, 매입가 대비 또는 직전 거래 대비)
- 카드 상세: 추이 그래프(월 단위, 1년·3년·5년·10년·보유 기간), 내 매입 거래, 최근 거래 목록, 건물 정보

### 제외

- 회원가입, 로그인, 소유주 인증
- 임대 계약 정보(보증금, 월세, 계약 만료일), 알림
- 세금·대출·중개비를 반영한 수익 계산
- 관리 지수(AMI), 전월세 시세, 장기수선충당금, 정산 관련 기능
- 데스크탑 전용 레이아웃, 관리자 화면
- 화면에 표시되는 더미 데이터 (단위 테스트에서 M0에 저장한 실제 응답 표본을 쓰는 것은 허용)

## 3. 전제

- 사용자: 로그인 없이 "이미 로그인된 임대인 1명"의 시점에서 시작한다. DB에는 고정 사용자 1명(id=1)을 만들어 두고 모든 자산을 그 사용자에 연결한다.
- 지역: 서울 25개 자치구로 제한한다.
- 화면: 모바일 폭(기준 390px)만 만든다. 넓은 화면에서는 최대 폭 480px로 가운데 정렬한다.
- 실행 환경: 한 대의 컴퓨터에서 화면, 서버, DB를 함께 실행한다. 배포는 하지 않는다.
- 데이터: 실제 API와 실제 단지만 사용한다.

## 4. 기술 스택과 구조

- 화면: Vue 3 + Vite. 라우터는 vue-router.
- 서버: Node.js(20 이상) + Express.
- DB: SQLite. 드라이버는 better-sqlite3를 권장한다.
- 그래프: 라이브러리는 자유(ECharts, Chart.js 등). 요구사항은 계단형 선, 거래 점, 점선 기준선, 터치 시 값 표시다.
- 테스트: 7장의 핵심 로직(가격, 매칭, 시계열)은 단위 테스트를 작성한다.

권장 폴더 구조:

```
/client        Vue 3 화면
/server        Express 서버, 수집 모듈, 로직
/server/data   SQLite 파일 (git 제외)
/docs          api-notes.md, verification.md
.env           인증키 (git 제외, 이미 존재)
.env.example   변수 이름만
PRD.md
```

- `npm run dev` 한 번으로 서버와 화면이 함께 뜨게 한다.
- `.gitignore`에 `.env`, `server/data/`, `node_modules/`를 넣는다.

환경 변수:

```
DATA_GO_KR_SERVICE_KEY=   # 공공데이터포털 일반 인증키(Decoding)
```

- `.env`에는 Decoding 키가 들어 있다. 요청을 만들 때 한 번만 URL 인코딩한다(URLSearchParams 사용). 이중 인코딩하면 "등록되지 않은 키" 오류가 난다.
- 공공데이터 호출은 서버에서만 한다. 화면은 서버의 `/api`만 호출한다.

## 5. 외부 API

네 API 모두 공공데이터포털(data.go.kr)의 국토교통부 API이며 같은 인증키를 쓴다. 아래 "확인"은 2026-10-05에 포털 상세 페이지에서 확인한 내용이고, "미확인"은 M0에서 실제 응답으로 확인해야 하는 내용이다.

| API | 용도 | 개발계정 트래픽 | 형식 |
|---|---|---|---|
| 국토교통부_아파트 매매 실거래가 상세 자료 | 현재가, 추이, 매입 거래 매칭 | 10,000 | XML |
| 국토교통부_건축HUB_건축물대장정보 서비스 | 동·호의 전용면적과 층 | 10,000 | XML 기본, `_type=json` 가능 |
| 국토교통부_공동주택 단지 목록제공 서비스 | 단지 검색용 목록 | 5,000 | JSON |
| 국토교통부_공동주택 기본 정보제공 서비스 | 준공 연도, 세대수, 주차 대수 | 5,000 | JSON |

### 5.1 아파트 매매 실거래가 상세 자료

- 확인: `GET https://apis.data.go.kr/1613000/RTMSDataSvcAptTradeDev/getRTMSDataSvcAptTradeDev`
- 확인: 요청 변수 `serviceKey`, `LAWD_CD`(법정동 코드 앞 5자리, 시군구 단위), `DEAL_YMD`(계약 연월 6자리), `pageNo`, `numOfRows`
- 확인: 동 정보, 층 정보, 해제 여부, 등기일자가 응답에 포함된다.
- 미확인(예상 필드명): `aptNm`, `aptSeq`, `aptDong`, `excluUseAr`, `floor`, `dealYear`, `dealMonth`, `dealDay`, `dealAmount`(만원 단위, 쉼표 포함 문자열), `umdNm`, `umdCd`, `sggCd`, `jibun`, `bonbun`, `bubun`, `buildYear`, `cdealType`(해제 여부), `cdealDay`, `rgstDate`
- 호출 단위가 "시군구 × 월"이다. 한 번의 호출로 그 구의 그 달 거래 전체가 온다. `totalCount`가 `numOfRows`보다 크면 다음 페이지를 이어서 받는다.
- 호수는 제공되지 않는다. 동 정보와 등기일자는 오래된 거래에는 비어 있을 수 있다.

### 5.2 건축HUB 건축물대장정보 서비스

- 미확인(예상): 기본 주소 `https://apis.data.go.kr/1613000/BldRgstHubService`, 전유공용면적 조회 오퍼레이션 `getBrExposPubuseAreaInfo`
- 미확인(예상): 요청 변수 `sigunguCd`(5자리), `bjdongCd`(5자리), `platGbCd`(0 대지, 1 산), `bun`(4자리), `ji`(4자리), `dongNm`, `hoNm`, `pageNo`, `numOfRows`, `_type=json`
- 응답에서 전유/공용 구분이 "전유"인 행의 면적을 전용면적으로 쓴다. 층 번호도 같은 응답에서 얻는다.
- 동·호 표기는 단지마다 다르다("101동"/"101", "1203호"/"1203"). 여러 표기를 차례로 시도한다.

### 5.3 공동주택 단지 목록제공 서비스

- 확인: 기본 주소 `https://apis.data.go.kr/1613000/AptListService4`, 시도별 목록 오퍼레이션 `getSidoAptList4`, 요청 변수 `serviceKey`, `sidoCode`, `pageNo`, `numOfRows`
- 미확인(예상): 응답 필드 `kaptCode`(단지코드), `kaptName`, `bjdCode`(법정동 코드 10자리), `as1`~`as4`(주소 구성)
- 서울의 시도 코드는 11이다. 서울 단지 목록 전체를 최초 1회 받아 DB에 저장하고, 단지 검색은 저장된 목록에서 한다.
- 이 목록은 공동주택관리정보시스템(K-APT)에 가입한 단지만 포함한다. 소규모 단지가 검색되지 않는 것은 PoC의 알려진 한계로 둔다.

### 5.4 공동주택 기본 정보제공 서비스

- 확인: 기본 주소 `https://apis.data.go.kr/1613000/AptBasisInfoServiceV5`, 상세 정보 오퍼레이션 `getAphusDtlInfoV5`, 요청 변수 `ServiceKey`, `kaptCode`
- 미확인(예상): 기본 정보 오퍼레이션 `getAphusBassInfoV5`. 응답 필드 `kaptAddr`(법정동 주소), `doroJuso`, `bjdCode`, `kaptdaCnt`(세대수), `kaptDongCnt`(동 수), `kaptUsedate`(사용승인일), 주차 대수(`kaptdPcnt` 지상, `kaptdPcntu` 지하로 예상)
- 자산을 등록할 때 그 단지에 대해 1회 호출하고 저장한다.

### 5.5 호출 규칙

- K-APT 계열 API는 주소의 버전 숫자가 바뀌어 왔다. 404가 나면 포털 상세 페이지에서 현재 버전을 확인한다.
- 받은 응답은 모두 DB에 저장하고, 이미 받은 "시군구 × 월"은 다시 호출하지 않는다(재수집 규칙은 7.8).
- API별 당일 호출 횟수를 DB에 기록한다. 한도의 90%에 도달하면 추가 호출을 멈추고 화면에 안내한다.
- 호출은 순차로 하고 실패 시 간격을 두고 최대 2회 재시도한다.
- 승인 직후에는 키가 등록되지 않았다는 오류가 날 수 있다. 이 경우 코드 문제로 단정하지 말고 사용자에게 알린다.

## 6. 데이터 모델

테이블과 핵심 열만 적는다. 열 이름과 세부 타입은 구현하면서 정한다.

- `users`: id. 고정 사용자 1명.
- `complexes`: kapt_code(PK), 이름, bjd_code, sigungu_code, 법정동 이름, 주소, 지번(본번·부번), 세대수, 사용승인일, 주차 대수, 실거래가 쪽 단지 식별값(7.1), 상세 정보 수집 시각
- `assets`: id, user_id, kapt_code, 동, 호, 층, 전용면적, 면적 출처(auto/manual), 취득 연월, 매입가(만원), 매입 계약일, 매입가 출처(matched/manual/없음), 생성 시각
- `trades`: 시군구 코드, 계약 연월, 단지 식별값, 단지 이름, 법정동, 지번, 전용면적, 층, 동, 계약일, 거래금액(만원 정수), 해제 여부, 등기일자. 같은 거래가 중복 저장되지 않게 유일 키를 둔다.
- `fetch_log`: 시군구 코드, 계약 연월, 수집 시각, 건수. 어떤 달이 저장돼 있는지 판단하는 기준이다.
- `api_usage`: API 이름, 날짜, 호출 횟수

금액은 만원 단위 정수로 저장한다.

## 7. 핵심 로직

### 7.1 단지 연결

K-APT의 단지(kapt_code)와 실거래가 자료의 단지를 연결해야 한다. 두 자료의 단지 이름 표기가 달라 이름만으로는 맞지 않는다.

1. 법정동 코드와 지번(본번·부번)으로 연결한다. K-APT 주소에서 지번을 얻는 방법은 M0에서 정한다.
2. 지번으로 연결되지 않으면 같은 법정동 안에서 정규화한 이름(공백, "아파트", 괄호 제거)으로 비교한다.
3. 그래도 연결되지 않는 단지는 "이 단지는 실거래가를 연결할 수 없습니다"로 안내하고 등록을 막는다.

건축물대장 조회에 필요한 지번도 이 연결 결과에서 얻는다.

### 7.2 전용면적과 층 자동 조회

1. 단지의 시군구 코드, 법정동 코드, 지번과 입력한 동·호로 건축물대장 전유공용면적을 조회한다.
2. 성공하면 전용면적과 층을 자동으로 채운다.
3. 실패하면 직접 입력으로 전환한다. 이때 전용면적은 그 단지의 실거래가에 등장한 면적 목록에서 고르게 하고, 층은 호수에서 계산한 값(1203호는 12층)을 기본값으로 넣어 수정할 수 있게 한다.

### 7.3 "같은 단지·같은 면적"의 판정

- 같은 단지: 7.1에서 연결한 단지 식별값이 같다.
- 같은 면적: 전용면적 차이가 0.1㎡ 이하다.
- 해제된 거래는 모든 계산과 목록에서 제외한다.

### 7.4 현재가

같은 단지·같은 면적의 가장 최근 거래 1건의 금액이다. 계약일 기준이며, 항상 거래 시점(연월)과 함께 표시한다. 저장된 기간에 거래가 없으면 "거래 내역 없음"으로 표시한다.

### 7.5 증감 표시

- 매입가가 있으면 "매입가 대비": 현재가 − 매입가, 그리고 그 비율(소수 첫째 자리).
- 매입가가 없으면 "직전 거래 대비": 가장 최근 거래 − 그 직전 거래. 거래가 1건뿐이면 증감을 표시하지 않는다.
- 상승은 빨강과 "+", 하락은 파랑과 "−"로 표시한다. 색만으로 구분하지 않도록 부호를 항상 붙인다.
- 화면 문구는 "수익"이 아니라 "매입가 대비"다.

### 7.6 매입 거래 매칭

입력: 자산(단지, 전용면적, 층, 동)과 취득 연월.

1. 검색 기간은 입력한 달과 그 앞 3개월, 모두 4개월이다. 저장되지 않은 달은 먼저 수집한다.
2. 후보 조건: 같은 단지, 같은 면적, 같은 층, 해제 아님.
3. 거래에 동 정보가 있고 자산의 동과 같으면 후보 목록의 맨 위에 둔다. 동 정보가 다르면 후보에서 뺀다. 동 정보가 없는 거래는 그대로 후보에 둔다.
4. 후보 0건: 매입가 직접 입력 화면으로 간다.
5. 후보 1건: "이 거래가 맞나요?"로 확인받는다.
6. 후보 여러 건: 목록에서 고르게 한다.
7. 임대인이 확정한 거래의 금액과 계약일을 매입가와 매입 계약일로 저장한다(출처 matched). 직접 입력하면 금액과 취득 연월을 저장한다(출처 manual).
8. 취득 연월은 선택 항목이다. 입력하지 않거나 "건너뛰기"를 누르면 매입가 없이 등록한다.
9. 저장한 매입가는 상세 화면에서 수정하거나 삭제할 수 있다.

### 7.7 월별 시계열

그래프에 쓰는 값이다.

- 가로축은 월 단위다.
- 점: 그 달에 같은 단지·같은 면적 거래가 있으면, 그 달의 마지막 거래 금액으로 점을 찍는다.
- 선: 각 달의 값은 "그 달 말까지의 가장 최근 거래 금액"이다. 거래가 없는 달은 직전 값을 유지하므로 계단 모양이 된다.
- 조회 범위 시작 이전의 거래가 저장돼 있으면 그 값에서 선을 시작하고, 없으면 범위 안의 첫 거래부터 선을 시작한다.
- 매입가가 있으면 매입가를 가로 점선(기준선)으로 긋고, 매입 시점에 별도 표시를 찍는다.

### 7.8 데이터 로딩과 갱신

- 카드를 추가할 때: 그 자산의 시군구에 대해 최근 12개월(현재 월 포함)을 즉시 수집한다. 취득 연월이 있으면 매칭 검색 기간 4개월도 함께 수집한다.
- 기간 탭을 누를 때: 3년, 5년, 10년, 보유 기간에 필요한 달 중 `fetch_log`에 없는 달만 수집한다. 보유 기간은 매입 계약월(직접 입력이면 취득 연월)부터 현재 월까지다. 매입가가 없으면 보유 기간 탭을 숨긴다.
- 수집 중에는 진행 상황(예: 24개월 중 9개월)을 보여준다. 10년 탭은 추가로 최대 60회를 호출한다.
- 앱을 다시 열 때: 최근 3개월(현재 월과 직전 2개월)의 마지막 수집이 30일을 넘었으면 그 3개월만 다시 수집한다. 그보다 오래된 달은 다시 수집하지 않는다.
- 같은 시군구의 자산이 여러 개면 수집 결과를 함께 쓴다.

### 7.9 금액 표기

- 표시 형식은 "12억 4,000만", "7억 8,500만", "9,500만"이다. 억 단위가 딱 떨어지면 "12억"으로 쓴다.
- 증감도 같은 형식에 부호를 붙인다: "+1억 2,000만", "−1,500만".

## 8. 화면 명세

레퍼런스는 토스 증권의 종목 화면이다. 큰 숫자 하나, 그 아래 증감, 그래프, 기간 탭의 순서와 여백을 참고한다. 색과 로고는 가져오지 않는다.

모든 화면 하단 또는 상세 화면 하단에 다음 고지 문구를 둔다: "국토교통부 실거래가 기준의 참고용 정보이며 감정평가가 아닙니다. 세금, 대출, 중개비는 반영하지 않습니다."

### 8.1 홈 (내 자산)

- 상단: "내 자산"과 자산 수
- 자산 카드(자산당 1장): 단지명, 동·호와 전용면적, 최근 실거래가, 거래 시점("2026.08 거래"), 증감(7.5)
- 카드를 누르면 상세로 이동한다.
- 하단: "자산 추가" 버튼
- 상태: 자산 없음(등록 안내와 버튼만), 수집 중(카드 안에 진행 표시), 거래 내역 없음, 수집 실패(다시 시도 버튼)

### 8.2 자산 추가

1. 단지 검색: 단지명 일부를 입력하면 서울 단지 목록에서 후보를 보여준다(이름과 구·동).
2. 동, 호 입력
3. 자동 조회 결과: 전용면적과 층. 실패하면 7.2의 직접 입력으로 전환한다.
4. 취득 연월(선택): 연도와 월 선택
5. "등록하고 불러오기" 버튼: 자산을 저장하고 수집을 시작한다. 취득 연월이 있으면 8.3으로, 없으면 홈으로 간다.

### 8.3 매입 거래 확인

- 후보 1건: "이 거래가 맞나요?", 검색 기간 안내, 후보 카드(금액, 계약 연월, 층, 전용면적), "맞아요"와 "아니에요, 직접 입력"
- 후보 여러 건: 후보 목록에서 선택, "여기에 없어요, 직접 입력"
- 후보 0건: "거래를 찾지 못했어요", 이유 안내("상속, 증여, 분양이거나 실거래가 공개 이전의 취득은 자료에 없습니다"), 매입가 직접 입력, "저장"과 "건너뛰기"

### 8.4 카드 상세

위에서 아래 순서로 배치한다.

1. 단지명, 동·호, 전용면적
2. "최근 실거래가 · 2026.08 거래"와 큰 금액
3. 증감: "매입가 대비 +1억 2,000만 (+10.7%)" 또는 직전 거래 대비
4. 추이 그래프(7.7). 터치하면 그 달의 값과 거래 정보를 보여준다.
5. 기간 탭: 1년, 3년, 5년, 10년, 보유. 기본 선택은 1년이다. 1년치는 등록할 때 이미 수집돼 있어 상세 화면이 바로 열린다.
6. 내 매입 거래: 계약 연월, 층, 금액, 출처(자동 매칭/직접 입력), 수정과 삭제. 매입가가 없으면 "취득 연월 입력" 버튼.
7. 최근 거래: 같은 단지·같은 면적의 최근 5건(계약 연월, 층, 금액)
8. 건물 정보: 준공 연도, 세대수, 주차 대수
9. 자산 삭제(확인 후 삭제)

## 9. 서버 API 초안

경로와 응답 형태는 구현하면서 조정해도 된다.

- `GET /api/complexes?query=` 단지 검색
- `GET /api/units/lookup?kaptCode=&dong=&ho=` 전용면적·층 자동 조회
- `GET /api/assets` 자산 목록(카드에 필요한 값 포함)
- `POST /api/assets` 자산 등록과 초기 수집 시작
- `GET /api/assets/:id` 상세(최근 거래, 건물 정보, 매입 정보)
- `DELETE /api/assets/:id`
- `GET /api/assets/:id/series?range=1y|3y|5y|10y|hold` 월별 시계열. 필요한 달이 없으면 수집한 뒤 응답한다.
- `GET /api/assets/:id/progress` 수집 진행 상황
- `POST /api/assets/:id/purchase/candidates` 취득 연월을 받아 후보 반환
- `PUT /api/assets/:id/purchase` 매입가 저장(매칭 확정 또는 직접 입력)
- `DELETE /api/assets/:id/purchase`

## 10. 개발 단계

### M0. API 확인 (가장 먼저)

- 네 API를 실제로 호출해 주소, 요청 변수, 응답 필드명을 확인하고 `docs/api-notes.md`에 정리한다. 실제 응답 표본을 테스트용으로 저장한다.
- 노원구 하계동의 단지 3~5곳으로 세 가지 연결을 끝까지 확인한다: K-APT 단지 ↔ 실거래가 단지, 단지 지번 ↔ 건축물대장, 동·호 ↔ 전용면적·층.
- 완료 기준: 하계동 단지 최소 3곳에서 "단지 선택 → 동·호 → 전용면적 → 같은 단지·같은 면적 거래 목록"이 스크립트로 재현된다. 연결되지 않는 경우와 그 이유가 기록돼 있다.
- 이 단계에서 5장이나 7.1과 다른 사실이 나오면, 다음 단계로 가기 전에 사용자에게 요약해 알린다.

### M1. 서버 기반

- 프로젝트 구조, DB 스키마, 호출 모듈(인코딩, 재시도, 호출 횟수 기록), 서울 단지 목록 적재
- 완료 기준: 단지 검색 API가 서울 단지 이름으로 결과를 반환한다.

### M2. 자산 등록

- 단지 연결, 전용면적·층 자동 조회와 직접 입력 전환, 자산 저장과 삭제
- 완료 기준: 실제 호실을 API로 등록하면 전용면적과 층이 저장된다.

### M3. 수집과 가격

- 월 단위 수집과 `fetch_log`, 현재가, 증감, 월별 시계열, 재수집 규칙
- 완료 기준: 7.3~7.5, 7.7의 단위 테스트가 통과한다. 같은 달을 두 번 요청해도 외부 호출이 한 번만 일어난다.

### M4. 매입 거래 매칭

- 후보 검색, 확정, 직접 입력, 수정과 삭제, 보유 기간 범위
- 완료 기준: 7.6의 단위 테스트가 통과한다.

### M5. 화면

- 8장의 네 화면과 상태 처리, 그래프
- 완료 기준: 390px 폭에서 가로 스크롤이 없고, 등록부터 상세까지 화면만으로 진행된다.

### M6. 검증

- 11장의 시나리오와 지정 검증 사례를 실행하고 결과를 `docs/verification.md`에 기록한다.

## 11. 검증

### 11.1 시나리오와 성공 기준

| # | 시나리오 | 검증 내용 | 성공 기준 |
|---|---|---|---|
| 1 | 실제 호실 등록 | 단지 검색 후 동·호 입력 | 전용면적 자동 채움, 카드 생성 |
| 2 | 매입 거래 매칭 | 취득 연월 입력 | 같은 층 거래를 후보로 제시 |
| 3 | 매칭 실패 | 자료에 없는 취득 연월 | 직접 입력으로 매입가 저장 |
| 4 | 매입가 대비 표시 | 매입가가 있는 카드 | 금액과 비율, 그래프 기준선 표시 |
| 5 | 매입가 없는 카드 | 취득 연월 없이 등록 | 직전 거래 대비로 표시 |
| 6 | 기간 탭 전환 | 3년, 5년, 10년, 보유 선택 | 없는 달만 호출, 그래프 갱신 |
| 7 | 앱 재진입 | 닫았다가 다시 열기 | 재호출 없이 저장된 값 표시 |
| 8 | 거래 없는 면적 | 거래가 드문 호실 등록 | "거래 내역 없음" 표시, 오류 없음 |
| 9 | 해제 거래 포함 | 해제 건이 있는 달 조회 | 해제 건이 가격과 그래프에서 제외 |

### 11.2 지정 검증 사례 (사용자 지정)

- 지역: 서울 노원구 하계동. 단지는 직접 고른다.
- 취득일: 2016년 10월 17일. 취득 연월은 2016년 10월로 입력한다. 검색 기간은 2016년 7월부터 10월까지다.

두 가지를 모두 수행한다.

**사례 A. 자동 매칭.** 2016년 7~10월 하계동 거래 중 해제되지 않은 거래 하나를 고른다. 그 거래의 단지, 전용면적, 층에 해당하는 실제 호실(건축물대장에 존재하는 동·호)을 자산으로 등록하고 취득 연월을 2016년 10월로 넣는다. 고른 거래가 후보로 나오는지, 확정 후 카드에 매입가 대비가 표시되는지, 보유 기간 탭이 그 계약월부터 현재까지 그려지는지 확인한다.

**사례 B. 직접 입력.** 같은 기간에 거래가 없는 층의 호실을 등록해 매칭이 실패하는지 확인한다. 매입가는 같은 단지·같은 면적의 2016년 7~10월 거래 평균가(만원 단위 반올림)를 직접 입력한다. 그 기간에 거래가 없으면 2016년 전체 평균을 쓴다. 저장 후 카드와 그래프에 매입가 대비와 기준선이 표시되는지 확인한다.

`docs/verification.md`에 다음을 기록한다.

- 사용한 단지, 동·호, 전용면적, 층
- 사례 A에서 고른 거래와 화면에 나온 후보의 일치 여부
- 사례 B에 입력한 평균가와 그 계산에 쓴 거래 목록
- 시나리오 1~9의 통과 여부와 통과하지 못한 경우의 원인
- 검증에 쓴 API별 호출 횟수

## 13. 비기능 요구사항

- 보안: 인증키는 서버에서만 읽는다. 응답, 로그, 오류 메시지, 문서, 커밋에 키가 들어가지 않게 한다. 외부 호출 URL을 로그에 남길 때는 키를 가린다.
- 오류 처리: 외부 API 실패, 한도 초과, 단지 연결 실패, 면적 조회 실패 각각에 대해 화면에 원인과 다음 행동을 한 문장으로 안내한다.
- 성능: 화면 조회는 DB에 저장된 값으로 응답한다. 외부 호출이 필요한 요청은 진행 상황을 보여준다.
- 정확성: 금액 계산은 만원 단위 정수로 한다. 화면의 숫자는 모두 저장된 실제 거래에서 나온 값이어야 한다.
