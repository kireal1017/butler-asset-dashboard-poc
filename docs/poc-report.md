## 2. 왜 만들었나

### 문제
- 기획서는 자산 현황 대시보드를 "국토부 실거래가와 건축물대장 API로 자산 가치를 실시간 추적하는 모듈"로 정의한다.
- 그러나 **단지 시세와 실거래가 그래프는 기존 무료 앱(호갱노노, 네이버 부동산 등)이 이미 제공**한다. 그대로 만들면 차별점이 없다.

### 제안
- 시세가 아니라 **"내가 산 가격 대비 지금 가격"**을 보여 준다.
- 임대인이 호실(동·호)을 등록하면 **층과 면적 단위**로 거래를 좁힐 수 있다.
- **취득 연월만** 입력하면 실거래 자료에서 **그 사람의 매입 거래를 찾아** 매입가로 쓴다. 매입가를 따로 기억하거나 서류를 찾을 필요가 없다.

### PoC가 증명할 것 (PRD 1장)
1. 단지와 동·호만으로 실제 호실을 등록할 수 있다.
2. 그 호실의 최근 실거래가와 추이를 **더미 데이터 없이** 실제 공공데이터로 보여 줄 수 있다.
3. 취득 연월만으로 매입 거래를 찾아 "매입가 대비"를 카드와 그래프에 표시할 수 있다.

## 3. 어떻게 동작하나

### 3.1 공공데이터 4종을 잇는 흐름

```mermaid
flowchart LR
  A[단지 목록<br/>K-APT] -->|단지 코드| B[단지 기본 정보<br/>K-APT]
  B -->|주소에서 지번 추출| C[실거래가 상세<br/>국토부]
  B -->|지번| D[건축물대장<br/>국토부 건축HUB]
  D -->|동·호 → 전용면적·층| E((내 호실))
  C -->|같은 단지·같은 면적 거래| E
  E --> F[현재가 · 증감 · 추이 · 매입 거래]
```

| 단계 | 사용 API | 하는 일 |
|---|---|---|
| ① 단지 찾기 | 공동주택 단지 목록 | 서울 3,405개 단지를 이름으로 검색 |
| ② 위치 확인 | 공동주택 기본 정보 | 주소에서 지번을 뽑고 세대수·준공 연도·주차 대수를 가져옴 |
| ③ 호실 확인 | 건축물대장 전유공용면적 | 동·호로 **전용면적과 층을 자동 조회** |
| ④ 거래 연결 | 아파트 매매 실거래가 상세 | 같은 지번의 실거래 단지를 찾아 **같은 면적(±0.1㎡)** 거래만 사용 |

### 3.2 핵심 계산 규칙
- **같은 단지:** 내 호실의 **동이 속한 건물**의 거래만 쓴다. 한 단지 안에서도 건물마다 면적이 미세하게 달라(예: 현대 84.95㎡ vs 우성 84.91㎡) 섞이면 가격이 오염되기 때문이다(사용자 결정).
- **같은 면적:** 전용면적 차이 0.1㎡ 이하. 면적은 1/10000㎡ 정수로 저장해 소수점 오차를 없앴다.
- **해제 거래 제외:** 계약 후 해제 신고된 거래는 현재가·그래프·매칭에서 모두 뺀다.
- **현재가:** 같은 단지·같은 면적의 가장 최근 실거래 1건.
- **증감:** 매입가가 있으면 매입가 대비, 없으면 직전 거래 대비. 금액과 비율에 항상 +/− 부호를 붙인다.
- **추이 그래프:** 월별로 그 달의 마지막 거래, 거래가 없는 달은 직전 값을 유지(계단형). 기간 1년·3년·5년·10년·보유.
- **매입 거래 매칭:** 취득 연월과 그 앞 3개월 안에서 같은 면적·같은 층 거래를 찾는다. 동 정보가 같으면 맨 위, 다르면 제외.

### 3.3 데이터 수집 방식
- 실거래가 API는 **"시군구 × 월" 단위로만 조회**된다. 그래서 받은 결과를 DB에 쌓아 두고 화면은 DB만 읽는다.
- 같은 달을 두 번 받지 않으며, 최근 3개월은 30일이 지나면 늦은 신고를 반영하려고 다시 받는다.
- 한 달 치를 받을 때 모든 페이지가 다 와야만 저장한다. 원본 응답도 함께 저장해 나중에 검증한다.

## 5. 검증 — 숫자가 맞다는 것을 어떻게 증명했나

### 5.1 세 겹의 검증

```mermaid
flowchart TB
  R[(저장한 원본 API 응답)] --> P1[앱 서버<br/>파싱·계산]
  R --> P2[독립 재계산 스크립트<br/>앱 코드 사용 금지]
  P1 --> API[서버 응답 값]
  P1 --> UI[화면 표시 값]
  P2 --> CMP{비교}
  API --> CMP
  UI --> CMP
  CMP --> OK[불일치 0]
  S[국토부 실거래가<br/>공개시스템] -.직접 대조.-> UI
```

| 검증 | 방법 | 결과 |
|---|---|---|
| 독립 재계산 | 앱 코드를 쓰지 않는 별도 스크립트가 원본 응답을 다시 파싱해 PRD 규칙대로 계산. 단지 범위와 기간 시작 월도 스스로 정함 | 거래 약 7만 건 행 단위 대조, 시계열 22개, 화면 값 72개 **불일치 0** |
| 공식 사이트 대조 | 국토부 실거래가 공개시스템에서 같은 단지를 직접 조회 | 하계 현대·우성, 경희궁자이2단지 최근 거래 **일치** |
| 화면 자동 점검 | 390px에서 모든 화면·기간 탭을 돌며 가로 넘침, 고지 문구, 콘솔 오류 확인 | 가로 넘침 0, 콘솔 오류 0 |

공식 사이트도 하계동 270번지를 "현대"와 "우성" 두 단지로 나눠 보여 준다. 동이 속한 건물로 범위를 좁힌 판단과 같은 구분이다.

### 5.2 대표 사례

| | 사례 A — 자동 매칭 | 사례 B — 직접 입력 |
|---|---|---|
| 호실 | 하계현대우성 112동 1001호 (84.91㎡, 10층) | 하계현대우성 112동 501호 (84.91㎡, 5층) |
| 취득 연월 | 2016-10 | 2016-10 |
| 매칭 결과 | 후보 2건 중 **2016-07-21 4억 3,000만** 확정 | 같은 층 거래 없음 → 직접 입력 **4억 3,850만** |
| 현재가 | 12억 5,000만 (2026-07) | 12억 5,000만 (2026-07) |
| 화면 표시 | 매입가 대비 **+8억 2,000만 (+190.7%)** | 매입가 대비 **+8억 1,150만 (+185.1%)** |

사례 A의 정답 거래는 개발 첫 단계(M0)에서 실제 데이터로 미리 정해 두었고, 화면 클릭만으로 그 거래가 후보에 나오는지 확인했다.

### 5.3 PRD 시나리오 9개
실제 호실 등록, 매입 거래 매칭, 매칭 실패, 매입가 대비 표시, 매입가 없는 카드, 기간 탭 전환, 앱 재진입, 거래 없는 면적, 해제 거래 포함 — **모두 통과**. 근거는 [검증 기록](verification.md) 4장.

- 예: 기간 탭을 3년→5년→10년으로 바꿀 때 실거래 API를 **정확히 없는 달만큼(24+24+60=108회)** 호출했고, 다시 3년을 눌렀을 때는 0회였다.
- 예: 같은 달에 정상 거래(7억 3,700만)와 해제된 거래(7억 1,500만)가 있으면, 앱은 정상 거래만 쓴다.

## 7. 한계와 다음 단계

### 7.1 데이터 품질 평가 요약 ([전문](data-quality.md))
- **가격·면적·층 등 계산에 필요한 값은 결측 0%**로, 표시되는 숫자는 정확하다.
- 다만 다음은 실제 서비스 전 보완이 필요하다.
  - **거래가 드문 자산:** 노원구 단지·면적 그룹의 34%는 최근 1년 거래가 0건이라 현재가가 오래되었을 수 있다.
  - **튀는 거래:** 최근 1건 기준이라 가족 간 직거래 같은 이상 거래가 현재가가 될 수 있다 (4.5의 툴팁 예시).
  - **늦은 해제 신고:** 해제의 14%는 계약 90일 이후에 신고되어, 최근 3개월만 다시 받는 규칙으로는 놓친다. → 개선 v2에서 12개월로 넓힘.
  - **최근 달 신고 지연:** 신고 기한이 30일이라 최근 1~2개월은 거래가 적게 보인다.
  - **검색되지 않는 단지:** K-APT 미가입 단지, 지번이 여러 개인 단지 일부.

### 7.2 개선 계획 (승인 대기)
- **1단계:** 숫자는 그대로 두고 **신뢰도(높음·보통·낮음) 하나**를 표시한다. 신뢰도가 낮으면 "최근 정상 거래 기준 금액"을 함께 보여 준다. 이상 거래는 직전 12개월 거래 최대 5건(직거래 제외)의 중앙값 대비 ±20%로 판정한다.
- **결정 완료(개선 v2):** 재수집 범위 3→12개월 적용, 현재가 기준은 유지(내 건물·같은 면적·최근 1건)하고 대신 비교 근거 3가지를 함께 보여 준다. 단지 묶음(학여울청구 등)은 남은 과제.
- **실서비스 전환 과제:** 소유주 인증(타인 호실 매입가 노출 방지), 야간 일괄 수집과 서버 DB, 운영 계정 트래픽 증설, 공공데이터 이용허락 범위 확인
- **지역 확대:** PoC는 PRD에 따라 서울 단지만 검색된다. API는 전국을 지원하므로 단지 목록을 다른 시도까지 적재하고(경기도처럼 큰 곳은 여러 페이지), 그 지역 단지 몇 곳으로 연결을 실측한 뒤 열면 된다. 계산·화면 코드는 바꿀 필요가 없다.
- **확장 아이디어:** 전월세 실거래가(전세가율·임대 시세), 신규 거래·해제 알림, 공시가격 연동

## 10. 개선 v2 — 내 호실 가격을 판단할 비교 근거 3가지

> 카드의 현재가는 "내 건물·같은 면적의 최근 1건"이라 한 건이 튀면 판단이 어렵다. 그래서 현재가는 그대로 두고, **상세 화면에 비교 근거 3가지**를 함께 보여 준다. 명세: [IMPROVEMENT-SPEC.md](IMPROVEMENT-SPEC.md) v2.1.

### 10.1 무엇을 추가했나
| 섹션 | 비교 대상 | 기간·범위 | 보여 주는 것 |
|---|---|---|---|
| 같은 층 거래 | 내 건물·같은 면적 중 **내 층** (없으면 ±2층) | 최근 3년 | 최근 5건, 건수 |
| 같은 단지의 비슷한 면적 | **단지 전체**(실거래 단지 여러 개 포함) | 최근 12개월, 내 면적 ±5㎡ | 중앙값·건수, 면적별 최근 거래 |
| ○○동 비슷한 면적 단지 시세 | 같은 법정동의 **다른 단지** | 최근 12개월, 내 면적 ±5㎡ | 중앙값·건수·단지 수, 단지별 최근 거래 |

### 10.2 값은 실측으로 정했다 (E0, [전문](e0-measure.md))
구현 전에 실제 DB로 기간·면적 범위·직거래 영향을 재고, 사용자가 값을 확정했다.

|---|---|---|

| 면적 범위 | 84㎡는 ±3과 ±5가 같음, ±10은 다른 평형이 섞임(장미 21→66건) | ±5㎡ |
| 단지·동네 기간 | 하계 자산 단지 21~24건, 동네 71~133건으로 충분 | 12개월 |
| 직거래 | 하계 84㎡ 중앙값 차이 0, 장미 59㎡ 단지만 2,500만 차이 | 포함 + 배지 |

### 10.3 기존 기능을 깨지 않았다는 증거
1. **변경 전후 나란히 비교:** 같은 DB의 사본 두 개로 변경 전 코드와 변경 후 코드를 동시에 띄워, 서버 응답 58개와 화면 값 72개가 **하나도 다르지 않음**을 확인했다. 비교하는 동안 두 DB의 내용도 바뀌지 않았다(외부 호출 0).
2. **기존 계산 코드 무수정:** 가격 계산 파일 변경 0줄, 기존 서비스 파일은 재수집 개월 수 한 줄만 바꿨다.
3. **신규 값 독립 재계산:** 앱 코드를 쓰지 않는 재계산 도구로 세 섹션을 다시 계산해 서버 응답 15개, 화면 값 132개(기존 72 + 신규 60)가 **불일치 0**.
4. **자동 테스트 131개 통과**(신규 26개: 중앙값, 층 확장, 면적 경계, 내 면적 묶음, 내 단지 제외, 수집 상태, 12개월 재수집).

### 10.4 확인한 한계
- **±2층 확장은 실데이터에서 결과가 있는 사례가 없었다.** 같은 층 0건인 자산(경희궁자이2단지)은 ±2층도 0건이었다. 확장 동작은 단위 테스트로 확인했다.
- **"내 면적" 줄과 카드 현재가가 다를 수 있다.** 사례 A는 카드가 우성 최근 거래(12억 5,000만), 내 면적 줄이 현대 최근 거래(9억 5,000만)다. 범위 차이를 조건 표시로 밝히지만, 같은 단지 안의 튀는 거래 문제(7.1)는 신뢰도 표시 계획에서 다룬다.
- **동네 목록의 단지 이름은 실거래 자료 기준**이라 K-APT 이름과 다를 수 있다(예: 학여울청구와 청구가 따로 표시).
- 동네 시세는 같은 법정동만 본다. 길 건너 다른 법정동 단지는 빠진다(좌표 기준은 범위 밖).
