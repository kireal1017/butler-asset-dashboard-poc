## 1. 배경과 목표

기존 PoC는 "내가 산 가격 대비 지금 가격"을 카드와 그래프로 보여 준다. 기획 의도는 단순 시세 조회가 아니라 **자산 관리**이며, 주식 앱(토스증권)이 매입가 선을 기준으로 등락을 설명해 주는 방식에서 출발했다.

이번 개선의 목표는 상세 화면에서 **"내 호실의 가격을 판단할 비교 근거 3가지"**를 함께 보여 주는 것이다.

| # | 비교 근거 | 한 줄 설명 |
|---|---|---|
| 1 | 같은 층 거래 | 내 호실과 가장 비슷한 거래 |
| 2 | 같은 단지의 비슷한 면적 | 우리 단지 안에서의 시세 |
| 3 | 같은 동네(법정동)의 비슷한 면적 단지 시세 | 우리 동네에서의 시세 |

부가 목표로, 늦게 들어오는 해제 신고를 놓치지 않도록 **재수집 범위를 3개월에서 12개월로** 넓힌다.

## 2. 범위

### 포함 (확정)
- 자산 상세 화면에 비교 근거 3개 섹션 추가
- 3개 섹션을 위한 서버 계산과 API
- 실거래 재수집 범위 3개월 → 12개월
- 독립 재계산 검증 도구 확장, 테스트 추가, 화면 캡처 추가

### 제외 (확정)
- **카드의 현재가와 증감 계산은 바꾸지 않는다.** 현재가는 지금처럼 "내 동이 속한 건물, 같은 면적(±0.1㎡), 최근 1건"이다. 기존 검증 값(화면 값 72개)이 그대로 유지되어야 한다.
- 홈 화면 카드 변경 없음
- 전국 단위 야간 일괄 수집 (발표에서 계획으로만 설명, 구현하지 않음)
- 신뢰도(높음·보통·낮음) 표시, 이상 거래 판정
- 소유주 인증, 로그인
- 좌표 기반 "반경 몇 m" 주변 단지 (좌표 API를 추가하지 않는다)

## 3. 화면 명세

### 3.1 배치 (확정)
홈에서 카드를 누르면 열리는 자산 상세 화면에서, **그래프와 기간 탭 바로 아래**에 세 섹션을 순서대로 둔다. 기존 섹션은 그 아래로 내려간다.

```
현재가 · 증감 칩            (변경 없음)
그래프 형태 선택 · 그래프    (변경 없음)
기간 탭                     (변경 없음)
────────────────────────
[신규 1] 같은 층 거래
[신규 2] 같은 단지의 비슷한 면적
[신규 3] ○○동 비슷한 면적 단지 시세
────────────────────────
내 매입 거래                (변경 없음)
최근 거래 (같은 단지·같은 면적)  (변경 없음)
건물 정보                   (변경 없음)
자산 삭제                   (변경 없음)
```

### 3.2 공통 규칙
- 모든 섹션은 **제목 옆에 조건을 작은 글씨로 표시**한다. 사용자가 "무엇과 비교한 숫자인지" 알 수 있어야 한다. (예: `같은 단지·같은 면적·10층`, `전용 79.91~89.91㎡ · 최근 12개월`)
- 요약 값을 보여 줄 때는 **거래 건수를 항상 함께** 표시한다. (예: `중앙값 11억 9,500만 · 거래 23건`)
- 계약이 해제된 거래는 모든 섹션에서 제외한다. (기존 규칙과 동일)
- 금액 표기, 날짜 표기, 직거래 배지, 카드·칩 스타일은 기존 Clay 토큰과 기존 "최근 거래" 섹션의 형식을 그대로 쓴다. 새 색이나 새 글자 크기를 만들지 않는다.
- 폭 390px에서 가로 넘침이 없어야 한다. 단지명이 길면 말줄임 처리한다.
- 세 섹션은 **참고 정보**다. 현재가나 증감 칩의 숫자에 영향을 주지 않는다.

### 3.3 [신규 1] 같은 층 거래

| 항목 | 내용 |
|---|---|
| 제목 | `같은 층 거래` |
| 대상 | 현재가와 같은 범위(내 동이 속한 건물, 같은 면적 ±0.1㎡) 중 **내 호실과 같은 층**의 거래 |
| 기간 | 최근 36개월 (`실측 후 확정`) |
| 표시 | 최근 순으로 최대 5건. 한 줄에 계약 연월, 층, 금액. 섹션 상단에 건수 |
| 같은 층 거래가 0건일 때 (확정) | **±2층으로 넓혀서** 보여 주고, 제목 옆 조건에 `±2층 기준`이라고 표시한다. 각 줄에 실제 층을 표시한다 |
| ±2층도 0건일 때 | `최근 3년간 비슷한 층 거래가 없어요` 같은 한 문장 안내. 오류로 처리하지 않는다 |

- 층 범위를 넓힐 때 1층 미만은 제외한다.
- 층 값이 없는 거래는 제외한다(현재 실데이터 결측 0%).
- 내 매입 거래로 확정된 거래도 목록에 포함한다(제외하지 않는다). 재수집 뒤 그 거래가 해제로 바뀌면 목록에서는 빠지고, 매입가는 자산에 복사해 둔 값이므로 그대로 남는다.
- 조건 표시 예: `같은 단지·같은 면적·10층`, 확장 시 `같은 단지·같은 면적·±2층 기준`.

### 3.4 [신규 2] 같은 단지의 비슷한 면적

| 항목 | 내용 |
|---|---|
| 제목 | `같은 단지의 비슷한 면적` |
| 대상 (확정) | **단지 전체**. K-APT 단지에 연결된 실거래 단지를 모두 포함한다(예: 하계현대우성 = 현대 + 우성). 현재가의 "내 건물만" 범위와 다르다는 점에 주의 |
| 면적 범위 | 내 전용면적 ±5㎡ (`실측 후 확정`) |
| 기간 | 최근 12개월 (`실측 후 확정`) |
| 요약 | 범위 안 거래의 **중앙값**과 거래 건수 |
| 목록 | 면적별로 묶어 한 줄씩: 전용면적, 최근 거래가, 계약 연월, 건수. 내 면적과 같은 줄에는 `내 면적` 표시. 최대 5줄 |
| 직거래 | 포함 (`실측 후 확정`). 목록의 최근 거래가 직거래면 기존 직거래 배지 |
| 0건일 때 | 한 문장 안내 |

- **면적 묶음 규칙 (확정, v2.1):** 기존 "같은 면적(±0.1㎡)" 규칙은 두 값을 비교하는 규칙이라 여러 값을 묶는 데 그대로 쓰면 처리 순서에 따라 결과가 달라진다. 그래서 **내 면적을 기준으로 고정**한다.
  - 내 면적과 ±0.1㎡ 이내인 거래는 모두 `내 면적` 한 줄. 면적 표시는 섞인 신고 면적을 모두 보여 준다(예: `84.91·84.95㎡`).
  - 나머지 거래는 신고 면적값 그대로 한 줄씩.
  - 정렬: `내 면적` 줄 맨 위, 나머지는 내 면적과 가까운 순, 같으면 작은 면적 먼저.
  - 사례 A 기대: 하계현대우성은 실거래 자료에서 현대(84.95㎡)와 우성(84.91㎡)으로 나뉘며, `내 면적` 줄에 두 단지의 거래가 함께 들어간다. 카드의 현재가(우성만)와 금액이 다를 수 있으므로 조건 표시로 범위를 밝힌다.
- 제목 옆 조건에 `단지 전체 기준`임을 밝힌다. 카드의 현재가와 범위가 다르기 때문이다. 예: `전용 79.91~89.91㎡ · 최근 12개월 · 단지 전체 기준`.
- 내 동의 실거래 단지를 모르는 자산(현재가가 이미 단지 전체를 보는 경우)도 조건 표시는 같다.
- 실거래 단지 연결이 없는 자산(지번 연결·이름 연결 모두 실패): 빈 상태 안내.

### 3.5 [신규 3] 같은 동네 비슷한 면적 단지 시세

| 항목 | 내용 |
|---|---|
| 제목 | `{법정동} 비슷한 면적 단지 시세` (예: `하계동 비슷한 면적 단지 시세`) |
| 대상 (확정) | 내 단지와 **같은 시군구, 같은 법정동**의 다른 실거래 단지. 내 단지(위 3.4의 단지 전체)는 제외 |
| 면적 범위 | 내 전용면적 ±5㎡ (`실측 후 확정`) |
| 기간 | 최근 12개월 (`실측 후 확정`) |
| 요약 | 범위 안 전체 거래의 **중앙값**, 거래 건수, 단지 수 |
| 목록 | 단지별 한 줄: 단지명, 최근 거래가, 계약 연월, 건수. 최근 거래 순. 기본 5개, 나머지는 `더 보기`로 펼침 |
| 0건일 때 | 한 문장 안내 |

- 평균이 아니라 **중앙값**을 쓴다(확정). 직거래 같은 튀는 거래 한 건이 값을 크게 흔들기 때문이다.
- 단지를 나누는 기준은 실거래 자료의 단지 식별 값 `aptSeq`(DB `trades.apt_seq`, 결측 0%)로 한다. 표시 이름은 그 단지의 가장 최근 거래의 단지명(`apt_nm`).
- 법정동은 내 K-APT 단지의 법정동 코드(`complexes.bjd_code`의 5~10자리)와 실거래의 법정동 코드(`trades.umd_cd`)가 같은 것으로 정한다. 제목의 동 이름은 `complexes.umd_name`. 좌표나 거리 계산은 하지 않는다.
- 실거래 단지 연결이 없는 자산은 내 단지를 제외할 수 없으므로 계산하지 않고 `내 단지를 실거래 자료에서 찾지 못해 동네 시세를 계산하지 않았어요` 안내.
- 직거래: 포함 (`실측 후 확정`).
- 신축과 구축이 섞일 수 있으므로, 요약 값 하나만 보여 주지 않고 **단지별 목록을 반드시 함께** 보여 준다.

## 4. 서버 명세

### 4.1 계산
- 세 섹션의 계산은 기존 가격·시계열 계산과 **같은 원천(DB에 저장된 실거래 행)**을 쓴다. 새 외부 API는 추가하지 않는다.
- 같은 시군구의 실거래는 이미 시군구×월 단위로 통째로 저장되므로, 3.5도 추가 호출 없이 계산할 수 있다. 다만 **필요한 달이 DB에 없으면** 기존 수집 흐름(없는 달만 호출, 한도 90% 차단)을 그대로 써서 채운다.
- 중앙값: 건수가 짝수이면 가운데 두 값의 평균. 결과는 만원 단위 정수로 반올림한다. 반올림 규칙을 한 곳에 정의하고 독립 재계산 도구와 일치시킨다.
- 기간 "최근 N개월"은 기존 기간 탭과 같은 방식이다(확인됨): 날짜가 아니라 **기준 월** 단위로, 기준 월(`AS_OF` 설정이 있으면 그 값, 없으면 한국 시간 이번 달)을 포함해 거꾸로 N개월. 예: 기준 월 2026-10, 36개월 → 2023-11~2026-10.

### 4.2 API (초안)
기존 상세 응답에 필드를 붙이지 말고 **별도 엔드포인트**로 둔다. 그래프와 현재가가 먼저 뜨고, 비교 근거는 뒤따라 떠도 되기 때문이다.

```
GET /api/assets/:id/comparisons          (읽기 전용 — 외부 호출을 하지 않는다)
→ {
    sameFloor:   { status, progress?, error?, floorRange: {min, max, widened}, months, count, trades: [...] },
    sameComplex: { status, ..., areaRange: {min, max}, months, count, median, groups: [...] },
    neighborhood:{ status, ..., dong, areaRange: {min, max}, months, count, complexCount, median, complexes: [...] }
  }
  status: ready | missing | collecting | failed   (섹션마다 따로)

POST /api/assets/:id/comparisons/collect  → 202 (빠진 달 수집 시작)
```

- 실제 필드명은 기존 API 규칙에 맞춘다.
- **섹션별 상태 (v2.1):** 세 섹션은 필요한 기간이 다르다(같은 층 36개월, 단지·동네 12개월). 한 응답이 가장 느린 섹션을 기다리지 않도록 섹션마다 상태를 따로 돌려준다. 준비된 섹션은 먼저 표시한다.
- **수집:** 조회(GET)는 수집을 시작하지 않는다. 화면은 `missing` 섹션이 있을 때 POST를 한 번 보낸다. 같은 층의 36개월은 3년 기간 탭과 같은 달이므로 같은 수집 작업(진행률)을 함께 쓴다. 단지·동네의 12개월은 자산 등록 때 수집하는 범위 안이다.
- 수집에 실패한 섹션은 자동으로 다시 수집하지 않는다(호출 한도 보호). `다시 시도` 버튼이 POST를 한 번 보낸다.
- 섹션 자리에만 진행 상태를 보여 주고, 화면 전체를 막지 않는다.
- 수집 실패와 한도 초과도 기존 문구와 `다시 시도` 버튼을 재사용한다.

### 4.3 재수집 범위 변경 (확정)
- 최근 **12개월**에 해당하는 달은 마지막 수집 후 30일이 지나면 다시 받는다. (기존: 최근 3개월)
- 근거: 해제 신고의 14%가 계약 90일 이후에 들어온다(`data-quality.md`).
- 이 변경으로 늘어나는 호출 횟수(시군구 1곳 기준 30일마다 최대 12회)를 `api-notes.md`에 기록한다.
- 재수집 후 기존에 확정된 매입 거래가 해제된 것으로 바뀌는 경우의 처리는 기존 동작을 유지하고, 어떻게 동작하는지 보고한다.

## 5. 작업 단계

### E0. 실측 (구현 전, 보고 후 승인)
기존 DB(노원구, 종로구)로 아래를 측정해 표로 보고한다. 코드는 검증용 스크립트만 쓴다.

1. 등록된 자산 전부에 대해 세 섹션의 건수: 같은 층(±2층 확장 전/후), 같은 단지 ±5㎡, 같은 법정동 ±5㎡
2. 기간을 12·24·36개월로, 면적 범위를 ±3·±5·±10㎡로 바꿨을 때 건수가 어떻게 달라지는지
3. 3.4와 3.5에서 직거래를 포함할 때와 뺄 때 중앙값 차이
4. 3.4, 3.5에 필요한 필드(법정동, 단지 식별 값, 층)가 전 기간에 채워져 있는지 결측 비율
5. ±5㎡ 범위에 다른 평형 계열이 섞이는 자산
6. 사례 A의 기본 기간 같은 층 거래 목록 (6장 3항의 기대값으로 고정)
7. 같은 층 거래가 0건인 자산 (6장 4항 확인용)
8. 이 명세와 기존 구현이 어긋나는 점

보고 후 사용자가 `실측 후 확정` 값을 정한다. **승인 전에는 E1 이후를 시작하지 않는다.**

### E1. 서버
계산 함수, 엔드포인트, 재수집 범위 변경, 단위 테스트.

### E2. 화면
세 섹션 컴포넌트, 빈 상태·수집 중·실패 상태, 390px 점검.

### E3. 검증과 문서
아래 6장의 검증, 캡처 추가, 문서 갱신.

## 6. 검증 (완료 조건)

1. **회귀 없음 (v2.1)**: 재수집은 데이터를 정상적으로 바꾸므로, "값이 하나도 바뀌지 않는다"는 **같은 데이터에서** 확인한다.
   - 같은 기준 DB에서 사본 두 개를 만들고, **변경 전 커밋과 변경 후 코드**를 같은 `AS_OF`로 나란히 실행한다.
   - 두 서버의 자산 목록, 상세, 모든 기간 시계열 응답과 화면 값 72개가 같아야 한다. 200이 아닌 응답이 있으면 실패.
   - 실행 중 두 사본의 DB 내용(거래, 수집 기록, 연결 기록, 자산, API 사용량)이 바뀌지 않아야 한다(외부 호출 없음).
   - 변경 후 코드에서 기존 독립 재계산도 불일치 0.
   - 재수집 동작 자체는 7항의 단위 테스트로 따로 확인한다.
2. **신규 값 대조**: 독립 재계산 도구(앱 코드 import 금지)를 확장해 세 섹션의 건수, 중앙값, 목록의 금액을 다시 계산하고 서버 응답·화면 표시 값과 비교한다. 불일치 0.
3. **대표 사례 수기 확인**: 사례 A(하계현대우성 112동 1001호, 84.91㎡, 10층)의 세 섹션 값을 `verification.md`에 표로 남긴다.
   - 2016-07-21 4억 3,000만과 2016-10-13 4억 5,850만은 기본 기간(36개월: 2023-11~2026-10) 밖이므로 **기본 목록에는 나오지 않는 것이 정답**이다.
   - 기간을 늘린 단위 테스트에서는 두 건이 같은 층 목록에 들어오고, 매입 거래 확인 화면의 같은 층 후보와 같은 거래임을 확인한다.
   - 기본 기간의 기대 목록은 E0 실측 결과로 고정한다.
4. **확장 규칙 확인**: 같은 층 거래가 0건인 자산 하나를 찾아 ±2층 확장과 `±2층 기준` 표시가 동작하는지 확인한다.
5. **빈 상태 확인**: 거래가 드문 자산(종로구 경희궁자이2단지 207동 604호)에서 세 섹션이 오류 없이 안내 문구 또는 적은 건수로 표시되는지 확인한다.
6. **단지 범위 확인**: 3.4가 현대와 우성을 모두 포함하고, 3.5가 내 단지를 제외하는지 확인한다.
7. **재수집 확인**: 최근 12개월의 달이 30일 경과 후 다시 수집되고, 그보다 오래된 달은 다시 호출되지 않는다.
8. **자동 테스트**: 기존 105개 전부 통과 + 신규 테스트 추가. 중앙값(홀수·짝수·0건), 층 확장, 면적 경계값, 해제 제외, 내 단지 제외를 포함한다.
9. **화면 점검**: 390px 가로 넘침 0, 콘솔 오류 0, 하단 고지 문구 유지.
10. **보안**: 인증키 노출 검사 통과.
